# 智能问答模块增量 PRD —— 问答范围扩展至全模块

## 一、项目信息

- **语言**：简体中文
- **技术栈**：沿用现有 FastAPI + SQLAlchemy + SQLite（后端，`main.py`）、Streamlit（前端，`app.py`）、DeepSeek（LLM），增量开发，不引入新框架/依赖
- **项目**：科技项目管理系统（现有系统，`rd_platform`）
- **本次变更**：智能问答模块（`POST /ask` 及其检索/生成链路）检索范围扩展
- **原始需求复述**：优化智能问答模块，让它也能对合同、经费、成果、待办、项目元信息等结构化数据源进行智能问答，而不仅仅针对单个项目的文件资料；对「一共多少合同/合同总金额」「项目 X 到账经费」「已授权专利」「最近待办」「项目阶段」「合同甲方」等问题应能基于结构化数据准确回答，而不是回复"资料中没有找到相关内容"。

## 二、产品定义

### 产品目标

将智能问答模块的检索范围从「仅项目文件资料（ProjectFile）」扩展为「文件资料 + 合同/经费/成果/待办/项目元信息/文档摘要等结构化数据源」，使系统对**查找类**（甲方是谁、有哪些授权专利、项目处于什么阶段）与**统计类**（一共多少合同、总金额、到账经费）问题都能给出准确、可溯源的回答。

### 用户故事

1. 作为项目管理员，我想要问「我们一共有多少合同、合同总金额是多少」，以便快速掌握合同整体盘子，无需手工翻台账汇总。
2. 作为项目管理员，我想要问「项目 X 到账了多少经费」，以便快速了解单个项目的资金到位情况。
3. 作为科研管理人员，我想要问「有哪些已授权的专利」，以便快速盘点成果并定位相关专利台账。
4. 作为项目负责人，我想要问「最近有哪些待办」，以便及时处理到期提醒、避免漏项。
5. 作为普通用户，我想要问「项目 Y 处于什么阶段」「俄公堡项目的合同甲方是谁」，以便直接获取项目元信息与合同关键字段，无需逐页点开。

## 三、技术规范

### 需求池

#### P0（必须完成）

**R1｜检索数据源扩展**
- `_retrieve_context()`（`main.py` 第 63 行起）必须从「仅检索 `ProjectFile` 表」扩展为同时检索以下结构化数据源：`Contract`（合同）、`Funding`（经费）、`Achievement`（成果）、`Todo`（待办）、`Project`（项目元信息），并建议纳入 `DocumentSummary`（文档摘要）。
- 数据源枚举建议：`file / contract / funding / achievement / todo / project / document_summary`。

**R2｜结构化记录文本化（知识片段）**
- 每条结构化记录必须序列化为一条独立「知识片段」（record card）参与检索打分，不再走 1200 字切块逻辑（结构化记录本身短，一条即一块）。
- 文本化模板（字段拼接为自然语言，金额带单位、日期规范化，可空字段跳过）：
  - 合同：`【合同】《{contract_name}》编号{contract_no}，甲方{party_a}，乙方{party_b}，合同金额{amount_value}{currency}（含税{amount_incl_tax}，不含税{amount_ex_tax}），类型{contract_type}，签署日期{sign_date}，履约期限{term}，到期日{due_date}，质保金比例{warranty_ratio}，状态{status}，所属项目{project_name}`
  - 经费：`【经费】{project_name}，科目{item_name}，类型{fund_type}，金额{amount}元，日期{fund_date}，备注{remark}`
  - 成果：`【成果】{project_name}，名称{name}，类型{category}，状态{status}，权利人{holder}，取得日期{achieve_date}，备注{remark}`
  - 待办：`【待办】{category}，{title}，级别{level}，详情{detail}，状态{status}，关联模块{link}`
  - 项目：`【项目】{name}（编码{code}），当前阶段{stage}，简介{description}`
  - 文档摘要：`【资料摘要】{doc_type}：{summary}`
- 统一「知识片段」结构建议：`{ source_type, source_id, label, text, project_id, ref 相关字段 }`。

**R3｜统一打分与配额**
- 结构化片段必须复用现有关键词打分逻辑（`_expand_query` / `_fallback_terms` → 词频加权），并把「文件名命中加成」扩展为「名称/标题命中加成」（合同名、项目名、成果名、待办标题等）。
- 必须设置**每模块配额**（保底 + 上限，参照现有 `PER_FILE_CHUNKS` 思路），保证多个数据源公平竞争，避免某模块霸占 `top_k` 名额；具体数值由架构师定。

**R4｜统计类问题精确聚合**
- 必须识别统计意图（关键词如：一共/总共/多少/多少份/多少笔/合计/总计/求和/总金额/到账/分布），并将「合同总数与总金额、按项目的到账经费、按状态的成果/待办计数」等映射为**结构化 SQL 聚合**，得到精确数字后交给 LLM 组织语言。
- 原则：统计结果由代码精确计算，**不应**让 LLM 从检索片段中数数（易错）；LLM 只负责把精确数字转成自然回答并注明口径。
- 单项目筛选下统计仅针对该项目，全部项目下统计全库（与现有筛选语义一致）。

**R5｜references 来源区分与展示**
- references 必须新增 `source_type` 字段（区分文件/合同/经费/成果/待办/项目/摘要）。
- 结构化来源的跳转/下载方式：
  - 合同 → `download_url = /contracts/{id}/download`（已有），并可跳转合同台账；
  - 成果 → `download_url = /achievements/{id}/download`（有文件时，已有）；
  - 待办 → 用 `Todo.link` 字段跳转对应模块（无下载）；
  - 经费 → 无文件，跳转经费管理模块入口；
  - 项目 → 无文件，跳转项目详情/项目列表。
- 前端 `render_ask_page()` 的 references 渲染（`app.py` 第 1169-1185 行）必须按 `source_type` 差异化展示：文件类显示「⬇️ 下载」，结构化类显示「🔗 查看/跳转」。

**R6｜与「全部项目/单项目」筛选共存**
- `AskRequest.project_id` 筛选必须下推至所有结构化数据源（`Contract.project_id`、`Funding.project_id`、`Achievement.project_id`、`Project.id` 均已有；`Todo` 需通过 `source_id`/`link` 关联项目，或由架构师确定关联方式）。
- 选择单项目时，仅检索该项目的文件与结构化数据；选择全部项目时检索全库。

**R7｜生成提示词与接口参数更新**
- `_call_deepseek` 的 system prompt（`utils/ai.py` 第 94 行「仅依据资料回答问题」）必须更新，明确「可依据文件资料与结构化台账数据回答」。
- `AskRequest`（`main.py` 第 234 行）需新增范围参数（如 `sources: Optional[List[str]]`，默认 `None` = 全部/智能），由架构师定字段名。

#### P1（应该完成）

**R8｜前端范围选择控件**
- 在「选择要提问的项目」下方新增「问答范围」多选控件（详见 UI 交互设想），默认全选，用户可显式限定模块范围。

**R9｜智能意图路由**
- 用 LLM 对问题做一次模块路由（命中哪些数据源），减少无关片段噪声、降低 token 消耗；失败退回「全部数据源」。

**R10｜空结果兜底文案优化**
- 区分「该数据源无数据」与「知识库无内容」，并给出建议（如「合同模块暂无数据，请先录入合同」），不再笼统提示"资料中没有找到相关内容"。

**R11｜精确匹配优先**
- 合同编号、项目 code、成果名称等精确字段命中时优先排序（精确匹配权重高于普通词频）。

#### P2（可选完成）

**R12｜引用样式统一**
- references 在回答中表格化展示来源（类型图标 + 名称 + 跳转），与回答正文中的出处标注一致。

**R13｜性能优化**
- 避免每次提问全量序列化结构化表（缓存/按需增量），数据量较大时的延迟可控。

**R14｜前端模块跳转**
- 结构化引用可一键跳转到对应 Streamlit 模块页（结合 `Todo.link` / 前端 anchor）。

### UI 交互设想

- **范围控件位置**：在现有「选择要提问的项目」下拉框（`app.py` 第 1109-1116 行）正下方。
- **控件形式**：`st.multiselect` 多选，选项为带图标的模块标签：`📚 资料`、`📄 合同`、`💰 经费`、`🏆 成果`、`✅ 待办`、`📁 项目信息`；默认**全选**（即默认问全库，用户零学习成本）。
- **可选「智能」开关**：一个 `st.toggle`（「智能自动判断范围」）默认开启；开启时忽略手动多选，由后端意图路由决定命中模块；关闭时以后端 `sources` 为准。
- **references 展示**：按来源类型加前缀图标 + 来源名（文件/合同/成果显示「⬇️ 下载」，待办/经费/项目显示「🔗 查看」），保留现有片段 `snippet` 展示。
- **统计回答口径**：当问题命中统计意图时，在回答底部以小字展示「统计口径」（如「合同总金额 = 已确认合同金额求和，共 N 份」）。

### 待确认问题（Open Questions，交架构师/工程师决策）

1. **统计聚合实现方式**：预定义聚合函数 + 意图映射（推荐，安全确定）还是 LLM 生成 SQL（灵活但有风险）？建议前者。
2. **意图路由成本**：模块路由是否复用 `_expand_query` 同一次 DeepSeek 调用，还是单独一次调用 / 纯规则关键词？需权衡延迟与成本。
3. **结构化片段字段取舍**：各模块文本化时纳入哪些字段、顺序如何，空字段是否跳过，金额/日期格式规范。
4. **各模块配额数值**：每模块保底条数、上限条数、全局 `top_k` 上限的具体取值。
5. **Todo 与项目的关联**：`Todo` 表无直接 `project_id`，如何将待办纳入「单项目筛选」（经 `source_id` 反查源表、`link` 解析，或待办不做项目维度过滤）。
6. **前端既有分支是否收敛**：现有 `render_ask_page` 中 `is_doc → api_documents_summarize`、`is_stats → api_project_stats` 两分支（`app.py` 第 1136-1146 行，仅单项目可用）是否统一收敛到新的多模块 `/ask`，避免两套逻辑并存。
7. **DocumentSummary 去重**：摘要与 `ProjectFile` 全文并存时，如何避免同一内容重复命中、如何决定引用优先级。
8. **统计口径一致性**：合同总金额按「已确认/全部」口径、到账经费按 `fund_type` 口径，需与现有经费/合同统计模块口径对齐。
9. **references 跳转链接实现**：结构化来源的 `jump_url` 如何与 Streamlit 单页应用的状态切换衔接。

## 四、验收标准

以下 5 类示例问题必须在「全部项目」默认范围下给出正确、可溯源回答：

1. 「我们一共有多少合同？合同总金额是多少？」→ 返回精确合同数量与金额合计，并注明统计口径。
2. 「项目 X 到账了多少经费？」→ 返回该项目到账经费精确合计。
3. 「有哪些已授权的专利？」→ 列出已授权专利清单，附成果引用（可跳转/下载）。
4. 「最近有哪些待办？」→ 列出待办清单，附跳转链接。
5. 「项目 Y 处于什么阶段？」「俄公堡项目的合同甲方是谁？」→ 正确返回项目阶段 / 合同甲方。

补充判据：

- 选择「单项目」时，文件与结构化数据均仅返回该项目数据；选择「全部项目」时返回全库。
- references 中结构化来源能按 `source_type` 正确跳转或下载，不再只是文件下载链接。
- 结构化数据为空时返回有意义的兜底文案，而非"资料中没有找到相关内容"。
- **回归**：原有「仅文件资料」问答能力不受影响（默认范围包含文件，或用户手动选择「仅资料」仍可用）。
- 统计类回答的数字由后端精确聚合得出，LLM 不得自行估算/编造。
